# Events source contract discovery

Status: **E0 source endpoint captured; RSS payload inspection remains before the exit gate is complete.**

Research date: **2026-08-16**

This document records the source-contract discovery required by Phase E0 of `docs/events-and-jobs-roadmap.md`. It deliberately separates verified behavior from unresolved details so later ingestion code does not depend on a guessed endpoint.

## Official source

The source system is the **Events in Ostrobothnia / Ostrobothnia Events Calendar** operated in cooperation with the Regional Council of Ostrobothnia, KulturOsterbotten, Vaasa Region / City of Vaasa, VASEK, and Visit Vaasa.

Official calendar:

- https://events.osterbotten.fi/en/events/

Official information / FAQ:

- https://events.osterbotten.fi/en/feedback
- https://events.osterbotten.fi/fi/palaute-2/tietoa-tapahtumakalenterista/

The official documentation explicitly states that the RSS function can be used to import events and can be filtered by municipality or category.

## Verified RSS behavior

The RSS link on the unfiltered English calendar was observed using an `allEvents` RSS endpoint with explicit locale, limit, sort field, and sort direction parameters.

A municipality-filtered calendar page uses a query parameter shaped as:

```text
Municipalities[]=<municipality-id>
```

A filtered RSS control uses `EventService/search` and carries the municipality ID as:

```text
Municipalities=<municipality-id>
```

The important implementation rule is that the municipality ID must be captured from the calendar-generated filter/RSS URL. It must not be derived from the municipality display name.

## Vaasa municipality source capture

The repository owner manually selected **Vaasa** in the live English calendar and captured the resulting page URL on 2026-08-16.

The exact calendar URL generated for Vaasa was:

```text
https://events.osterbotten.fi/en/events?Keywords=&EventsFor=&DateFrom=&DateTo=&Municipalities%5B%5D=2&CurrentPage=1
```

This establishes the current Vaasa municipality value as:

```text
2
```

The RSS link generated by the same filtered page was captured exactly as:

```text
https://events.osterbotten.fi/EventService/search?Limit=100&Locale=en_US&Municipalities=2&SortField=Date&SortDir=ASC&Format=rss
```

This URL is the source contract to use for the E1 parser fixture and importer work unless a later source check shows that the calendar itself has changed it.

### Important path observation

The manually captured Vaasa RSS URL is rooted at:

```text
/EventService/search
```

rather than under `/en/events/EventService/search`.

E1 must use the exact calendar-generated URL above rather than reconstructing the path from earlier observations or page-local assumptions.

## Current page/filter contract

Observed public filter query parameters include:

```text
CurrentPage
DateFrom
DateTo
EventsFor
Keywords
Municipalities[]
Categories[]
```

For the captured Vaasa RSS URL, the server-side RSS search parameters are:

```text
Limit=100
Locale=en_US
Municipalities=2
SortField=Date
SortDir=ASC
Format=rss
```

Parameter order should not be treated as semantically significant by E1, but the values and generated endpoint must be preserved in the source fixture/documentation.

These values describe current source behavior, not an application-level guarantee. E1 should tolerate missing or changed optional item fields and validation should fail clearly if the source contract materially changes.

## Public calendar fields observed

The public event listing exposes the following field classes across current records:

- title;
- category;
- short description/summary where supplied;
- date or date range;
- start/end time where supplied;
- venue/location text;
- street/postal address where supplied;
- canonical event detail link.

The source also supports multilingual event entry. The official FAQ states that organizers can enter separate Finnish, Swedish, and English text variants while shared fields such as time and place are entered once.

## Stable identity and detail URL

The roadmap requirement remains:

- prefer a stable upstream event identifier when the RSS exposes one;
- otherwise derive the repository identity from the stable canonical detail URL;
- never derive identity from the display title.

The exact RSS item identity fields (`guid`, link shape, or equivalent) still need to be recorded from the raw Vaasa RSS payload.

## Headers, content type, and encoding

The exact response headers, MIME type, charset, XML declaration, and RSS item payload still need to be captured from the Vaasa RSS response.

Automated retrieval from the current agent environment was attempted after the Vaasa URL was supplied, but the web fetch returned a cache miss and the execution environment could not resolve the source hostname. Therefore no MIME type, charset, XML declaration, or item fields are claimed here without evidence.

Do not assume `application/rss+xml`, `application/xml`, or UTF-8 until the response is captured.

## Raw fixture requirement

Before E0 exits, save a small unmodified Vaasa RSS response under a test-fixture directory. The fixture should be source material for E1 parser tests, not production data.

The raw fixture is needed to determine:

- RSS/XML version and namespaces;
- item fields and optionality;
- `guid` or equivalent stable source identity;
- canonical detail URL shape;
- date/time representation and timezone information;
- whether venue/address/category/organizer are directly represented;
- whether multilingual variants are exposed in one feed or require another source request.

## Detail-page enrichment decision

No production detail-page enrichment is approved yet.

E1 must first inspect the raw Vaasa RSS fixture and map fields directly available in the feed. Detail-page fetches should only be added for a field that is required by the normalized contract and demonstrably absent from RSS.

The first release should remain conservative about copied content: title, time, category, venue/address, organizer when supplied, source URL, and only source-provided short summary text. Do not mirror images or long-form descriptions during E1.

## Feed/detail comparison requirement

After the raw fixture is available, compare 10-20 feed items against their canonical detail pages. Record whether the following are consistent:

- title;
- start/end date and time;
- venue and address;
- category;
- organizer when present;
- multilingual content availability;
- canonical URL and stable identity.

Any systematic field missing from RSS but required by the normalized event contract must be documented before introducing detail-page enrichment.
